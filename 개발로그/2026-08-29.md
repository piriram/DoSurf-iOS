## 무엇을

파고를 Open-Meteo 우선으로 읽도록 뒤집고(P0) TestFlight에 올렸다.
첫 업로드가 실행 즉시 크래시해서 원인을 잡고 재업로드했다.

## 왜

`FirestoreChartDTO.swift`가 파고를 기상청 `wave_height` 우선으로 읽고 있었다.
백엔드가 Phase 1에서 개선한 건 `om_wave_height` 쪽이라 개선이 화면에 도달하지
못하는 구조였다.

백엔드에서 실측해 보니 그냥 우선순위 문제가 아니었다. 기상청 파고는 지역별로
`0` 또는 `0.5`에 고정된 사실상 상수였고(API 원본 응답 확인), 같은 시각
Open-Meteo는 0.88~1.40으로 실제로 움직였다. **화면에 뜨던 파고가 거의 상수였다는
뜻이다.** 뒤집기는 선택이 아니라 필요한 수정이었다.

## 어떻게

한 줄이다.

```swift
// before
waveHeight: waveHeight ?? omWaveHeight ?? 0.0
// after
waveHeight: omWaveHeight ?? waveHeight ?? 0.0
```

기상청 값은 Open-Meteo가 없을 때의 폴백으로 남겼다. 화면 파고가 0.5에서
0.9~1.4로 올라가므로 사용자 공지가 필요할 수 있다.

`main`에 직접 커밋하지 않고 `fix/wave-height-priority` 브랜치를 파서 올렸다.

## 세션 2 — P1 파주기

### 무엇을

화면 파주기를 파랑모델의 실제 값(`wave.period_s`)으로 바꿨다.
풍속 기반 추정식은 지우지 않고 폴백으로 내렸다.

### 왜

문서에는 "추정치라 정확하지 않다"고만 적혀 있었고, 얼마나 틀린지는 아무도
재본 적이 없었다. **바로 켜지 말고 먼저 대조하라**는 주의도 함께 있었다.
그래서 코드를 고치기 전에 숫자부터 냈다.

백엔드 스케줄러가 아직 안 돌아 Firestore에 새 필드가 없었지만,
`scripts/open_meteo.py`가 인증 없이 돌아가므로 실제 파주기를 직접 받아
Firestore의 풍속으로 계산한 iOS 추정치와 맞대볼 수 있었다.

5개 해변 × 24시각 = 120개 비교 결과:

| | |
|---|---|
| 평균 차이 | +3.89초 (실제가 항상 더 길다) |
| 3초 이상 어긋난 시각 | 110/120 (92%) |
| 추정치가 clamp 바닥 2.0에 고정 | 92/120 (77%) |

원인이 둘로 갈렸다.

**clamp에 걸린다.** 식이 `0.83 × 풍속`이라 풍속이 2.41 m/s 이하면 결과가 항상
바닥값 2.0이 된다. 실측 풍속 범위가 0.1~5.8 m/s여서 대부분의 시각이 여기 걸렸다.
즉 **화면에 뜨던 파주기는 사실상 상수 2.0초였다.** 실제는 5~8초다.

**그라운드 스웰을 원리적으로 못 잡는다.** 속초·강릉·포항은 풍파 성분이 대부분
0인데 스웰만으로 5~6.8초가 나온다. 바람이 거의 없는 날에도 먼바다 스웰은
들어오는데, 풍속에서 유도한 값은 그걸 표현할 방법이 없다.

오늘 오전에 고친 파고(기상청 0/0.5 고정)와 **같은 모양의 문제**였다.
화면에 숫자가 떠 있으니 값이 있는 줄 알았는데, 실제로는 상수였다.

### 어떻게

```swift
let wave = data["wave"] as? [String: Any]
let wavePeriod = (wave?["period_s"] as? Double)
    ?? Self.estimateWavePeriod(...)
```

추정식을 지우지는 않았다. Phase 1 배포 전에 수집된 문서에는 `wave` 맵이 없어서
폴백이 필요하다. 대신 **측정 결과를 함수 docstring에 그대로 박아뒀다.**
"이 값을 믿지 말 것" + 평균 3.89초 오차 + clamp 77% + 스웰 문제.

`generic/platform=iOS Simulator` 빌드로 컴파일 확인했다. BUILD SUCCEEDED.

### 배운 점 / 다음 액션

**"부정확하다"와 "상수다"는 다른 문제다.** 문서에는 추정치라고만 적혀 있어서
오차가 좀 있는 값이라고 읽었는데, 실제로 재보니 77%가 같은 값이었다.
숫자를 내기 전과 후의 판단이 달라졌다 — 재보지 않았으면 "나중에 개선"으로
남겨뒀을 것이다.

**막힌 경로 옆에 안 막힌 경로가 있는지 본다.** Firestore에 새 필드가 없어서
스케줄러(20:15)를 기다릴 뻔했는데, Open-Meteo는 인증이 필요 없어 같은 데이터를
바로 받을 수 있었다. 대조에 필요한 건 Firestore가 아니라 그 값이었다.

**측정값은 코드 옆에 남긴다.** 개발로그에만 적으면 다음 사람이 함수를 볼 때
이 맥락에 닿지 못한다. docstring에 넣으면 그 함수를 건드리는 순간 읽게 된다.
